1) 仕様との不一致
- src/runner.js（ニアミス判定が広すぎる）
  - 設計書: 「横 1.2m 以内」ですれ違うとコンボ +1。
  - 実装: const nearMissWidth = 2.6; を用い、passObstacle 内で item.nearMiss = Math.abs(passX - item.x) < nearMissWidth; としており、隣レーン（中心間 2.2m）でも常にニアミス成立します。証拠: runner.js L12, L132–L137 付近。
- src/world.js（空フェーズの距離配分とパレット）
  - 設計書: フェーズ区間は 0–500m → 500–1500m → 1500–2500m → 2500m–（以降サイクル）で、背景色・フォグ・ライト色を滑らかに補間。
  - 実装: phaseColors を6段用意し、segment = (distance % 3000) / 500 に基づき 500m ごとに均等に遷移（全区間 500m 単位）しています。4フェーズの所定距離配分になっていません。証拠: world.js L3–L10, L92–L101。
  - さらに phaseColors に基調色以外（例: #a480e1, #3e6eb4, #8462d5, #593d59 など）を多用しており、「ビジュアルアイデンティティ（厳守）」の基調色セットから逸脱した配色が背景/ライトに混在しています。証拠: world.js L3–L10。
- vite.config（base 設定）
  - 設計書: Vite の base: './' を必ず設定し、モデル URL は import.meta.env.BASE_URL 基準。
  - 実装/構成: リポジトリに vite.config（または相当ファイル）が見当たりません。GLB 読み込みは BASE_URL に従っており良いものの、base 設定がないとサブパス配信時にビルド成果物（特に public/models/ 配下）へのパスが崩れる恐れがあります。証拠: vite.config.* が存在しない（提示バンドル内に未収載）。


2) バグ・不公平な生成・境界条件の問題
- ニアミスが意図より過剰に発生
  - 近接幅 2.6m のため、隣レーン通過（2.2m 差）でもほぼ必ずニアミスが付与され、スコア倍率が過大になりやすいです。ゲームバランス上不公平。証拠: runner.js L12, L132–L141。
- WebGL 初期化失敗時のエラーハンドリングが限定的
  - initializeRenderer は new THREE.WebGLRenderer の例外のみを捕捉し、UI のエラーメッセージ表示を行いますが、コンテキスト取得失敗が例外を投げない実装環境では検出できない可能性があります（無言で黒画面になりうる）。証拠: src/main.js L9–L18（try/catch のみ、追加検証なし）。


3) パフォーマンスとメモリの問題
- 重大な問題は確認できず
  - 障害物・ピックアップはプール再利用（runner.js）、pixelRatio 最大 2（world.js）、GLB 読み込み失敗時のフォールバック（models.js）など、要求に沿った実装になっています。


4) 良い点
- レーン座標（-2.2/0/2.2）、0.12秒のスムーズ補間と機体の傾き表現、操作（キーボード/スワイプ/左右タップ）、速度曲線（18→+0.35/s→max46）、障害物の挙動（クリスタルはジャンプのみ、バリアはダイブのみ、隕石はレーン回避のみ）、シールド/マグネット効果、ゲート通過時のフラッシュと+50点、HUD 表示、ポーズ（Esc/ボタン、タブ非表示時自動）、オブジェクトプール、BASE_URL を使った GLB パスなど、設計書の主要要件を丁寧に満たしています。
